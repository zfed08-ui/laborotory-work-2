# Лабораторная работа: асинхронность в Python на пальцах

По мотивам лекции «Асинхронное программирование в Python».  
Продолжительность: одна пара (90 минут).

## Цель

Руками прочувствовать, что такое корутина, точка переключения и event loop, без HTTP и внешних API. К концу работы вы должны уметь:

- объявить корутину и запустить её через `asyncio.run`;
- объяснить, почему `await` в цикле не даёт ускорения;
- запускать задачи конкурентно через `asyncio.gather` или `asyncio.create_task`;
- увидеть, как один блокирующий вызов замораживает весь event loop, и починить это.

## Подготовка

Нужен **Python 3.10** или новее. Сторонние библиотеки не требуются.

## Шаг 4. Блокировка event loop

Файл: `step4_blocking.py`. В заготовке уже лежит готовый асинхронный сервер из шага 3б, копировать ничего не нужно.

Теперь `bob` прислал не запрос к базе, а задачу на тяжёлые вычисления. В заготовке есть синхронная функция `heavy_compute()`, она считает 1–3 секунды в зависимости от машины.

### 4а. Ломаем

В `handle_request` для клиента `bob` вызовите `heavy_compute()` вместо `await asyncio.sleep(duration)`. Остальные клиенты по-прежнему ждут через `asyncio.sleep`. Запустите.

Ожидаемый вывод (время `bob` у вас будет своё):

```text
[  0.0s] alice: запрос принят
[  0.0s] bob: запрос принят
[  1.4s] bob: ответ отправлен
[  1.4s] carol: запрос принят
[  1.4s] dave: запрос принят
[  1.4s] eve: запрос принят
[  1.4s] alice: ответ отправлен
[  1.9s] carol: ответ отправлен
...
```

#### Контрольные вопросы

- `carol`, `dave` и `eve` не получили даже `запрос принят`, пока считал `bob`. Почему, ведь всё написано на `async`?
- Где точка переключения в `handle_request`, когда обрабатывается `bob`? Есть ли она вообще?

### 4б. Чиним

Вынесите `heavy_compute` из event loop, чтобы остальные клиенты не ждали `bob`. Два инструмента из лекции:

```python
await asyncio.to_thread(heavy_compute)
```

```python
from concurrent.futures import ProcessPoolExecutor

loop = asyncio.get_running_loop()
await loop.run_in_executor(pool, heavy_compute)
```

Во втором случае `pool` — это `ProcessPoolExecutor()`, откройте его через `with` внутри `main` и передайте в `handle_request` параметром.

Попробуйте оба варианта. Порядок строк должен стать как в шаге 3б: быстрые клиенты отвечают на 0.5 с, `bob` — последним. Время `bob` зависит от машины.

#### Контрольные вопросы

- Оба инструмента разблокировали event loop, и время у них, скорее всего, совпало. Но `heavy_compute` — это CPU-bound, а лекция говорит, что потоки для CPU-bound в Python не помогают из-за GIL. Почему поток всё-таки сработал здесь? Подсказка: пока `bob` считает в потоке, чем занят event loop?
- Куда бы вы вынесли синхронный `requests.get`, если бы он попался в корутине? Почему для него точно достаточно потока?

### 4в. Когда поток перестаёт спасать

Сделайте тяжёлыми трёх клиентов: `bob`, `dave` и `eve`. Запустите оба варианта из 4б и сравните общее время.

Ожидаемый результат:

- с `to_thread` три вычисления идут по очереди, общее время около трёх `heavy_compute`;
- с пулом процессов они идут параллельно, общее время около одного `heavy_compute`.

Почему потоки не дали параллелизма, а процессы дали? Сформулируйте правило: когда для блокирующего вызова хватает потока, а когда нужен процесс.
